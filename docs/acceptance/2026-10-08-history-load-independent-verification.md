## 已复现回归：失效符号链接被当作有效附件

位置：`Sources/HistoryStorage.swift:101–106`。

新的 `attributesOfItem` 会返回符号链接本身的属性。若 `blobs/<合法ID>` 是悬空符号链接，链接目标字符串的字节长度恰等于附件长度，写入流程会通过大小检查并跳过附件写入，最后成功保存索引。随后 `HistoryStorage.read` 无法读取附件，报告“历史内容文件缺失或损坏”。

独立复现直接编译当前真实 `HistoryStorage.swift`，并与 Git HEAD 中的同一文件对比；仅用最小 Codable 数据结构和非云环境桩替代外围依赖。准备目标为不存在的 `12345678` 的符号链接与 8 字节附件，结果如下：

- 当前版：`write=SUCCESS` → 附件仍为 `NSFileTypeSymbolicLink` → `read=FAIL`。
- HEAD：`write=SUCCESS` → 原子写入将链接替换为 `NSFileTypeRegular` → `read=SUCCESS bytes.equal=true`。

主 Agent 已检查 harness 并独立复跑得到相同结果。该复现使用 `/tmp` 专用数据，不涉及用户历史。建议写入时区分普通文件与符号链接；对悬空链接按既有行为安全替换，或明确拒绝，不能只比较链接自身大小后返回成功。补充悬空/越界/有效链接和已有损坏附件回归用例。产品源码尚未修复。
